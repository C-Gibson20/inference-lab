# Logging conventions

Inference Lab uses structured, contextual logs for operational visibility,
debugging, and profiling. Logs are local operational output and must not
contain document text, user queries, prompts, model outputs, credentials, or
other sensitive content.

Logging is configured during application startup, after settings are loaded and
validated and before application work begins.

## Architecture

Application code uses `structlog`. Python’s standard-library `logging` is the
underlying output and compatibility boundary.

This division keeps the application API focused while allowing dependencies
that emit standard-library records to share the same handlers and renderers:

- `structlog` provides event dictionaries, bound context, and processor
  pipelines.
- Standard-library handlers provide level filtering and the output stream.
- Third-party standard-library records can be rendered alongside application
  records.

Use `structlog` in `inference_lab` modules. Use standard-library logging only
for dependency integration and the process-level logging boundary.

Logging is configured once at application startup. Records go to stdout. The
application does not implement log-file rotation or retention; operators may
redirect stdout when a local file is required.

## Output formats

The renderer is selected through configuration:

| Format | Use |
| --- | --- |
| `console` | Readable output during local interactive development |
| `json` | One JSON object per line for scripts and tooling |
| `auto` | Console output on an interactive TTY; JSON otherwise |

The JSON renderer must preserve structured fields so profiling and operational
tools never need to parse human-readable messages.

## Record schema

Every record contains the following fields. A field remains present with a
`null` value when it is not applicable:

| Field | Meaning |
| --- | --- |
| `timestamp` | UTC timestamp generated by the logging pipeline |
| `level` | `debug`, `info`, `warning`, `error`, or `critical` |
| `event` | Stable snake-case name describing what happened |
| `module` | Emitting module or logger namespace |
| `pipeline_stage` | Current ingest, retrieval, serving, runtime, or evaluation stage |
| `document_id` | Stable document identifier, when applicable |
| `corpus_id` | Selected corpus identifier, when applicable |
| `corpus_version` | Corpus version being read or produced, when applicable |

Use `document_id` and `corpus_id` consistently; never substitute `doc_id` or a
corpus name. `corpus_id` remains useful before the first version exists or
while a new version is being staged. `run_id` and `request_id` may be added for
correlation. Profiling may add timing and resource fields.

Bind context at the boundary where it becomes known so nested stages inherit
it. Every operation targeting a corpus binds `corpus_id`; operations against a
published snapshot bind both `corpus_id` and `corpus_version`. Do not place
sensitive payloads in context merely to make them available to a log message.

## Log levels

| Level | Policy | Typical examples |
| --- | --- | --- |
| `DEBUG` | Diagnostic detail normally suppressed | Per-page, per-chunk, per-record, candidate, cache, or batch detail |
| `INFO` | Normal lifecycle and operational milestones | Stage or document completion, successful skips, normal abstention |
| `WARNING` | Unexpected condition handled without failing the current unit | OCR fallback, retry, degraded channel, malformed optional input, eviction |
| `ERROR` | The current unit of work failed | Failed document, query, stage, transaction, or benchmark case |
| `CRITICAL` | Process-wide failure requiring shutdown | Unrecoverable configuration or corrupted runtime state |

An empty result, abstention, duplicate, or no-op is not inherently a warning.
Use `WARNING` when the system recovered or continued with reduced capability.
Use `ERROR` when the affected unit did not complete successfully. Reserve
`CRITICAL` for failures that make continued execution unsafe.

Exceptions and tracebacks may be included when they explain an error, subject
to the same privacy requirements as ordinary records.

## Module policy

| Module | `DEBUG` | `INFO` | `WARNING` | `ERROR` |
| --- | --- | --- | --- | --- |
| `ingest` | Pages, chunks, parser details | Document and stage lifecycle; duplicate no-op | OCR fallback; skipped malformed optional content | Document or stage failure |
| `storage` / `provenance` | Repository and transaction details | Corpus-version advancement; commit completion | Retry; lock contention; recoverable migration issue | Failed transaction or persistence operation |
| `retrieval` | Channel candidates and scoring diagnostics | Query and stage completion, including zero results | Degraded channel; fallback path | Query or index operation failure |
| `serving` | Context assembly and token-budget diagnostics | Request completion; abstention; citation result | Backend fallback or degraded response | Failed request |
| `runtime` / `backends` | Batch, cache, scheduling, and memory details | Model load/unload; job lifecycle | Eviction; retry; fallback; near-budget condition | Backend or job failure |
| `profiling` | Fine-grained samples and measurement diagnostics | Stage timing and resource records | Incomplete or unreliable measurement | Failed benchmark unit |
| `evaluation` | Per-case diagnostics | Run and aggregate summaries | Invalid or missing evaluation input | Failed evaluation unit |
| `tooling` / configuration | Configuration-resolution detail | Startup, shutdown, selected configuration | Deprecated or recoverable setting | Invalid configuration preventing startup |

`INFO` describes normal operational milestones, not necessarily events visible
to an end user. `WARNING` describes recovery or reduced capability, not merely
an undesirable product outcome.

## Events and profiling

Event names are stable, machine-readable, and use snake case. Examples include
`document_started`, `stage_completed`, `document_skipped`, `ocr_fallback`,
`query_completed`, `benchmark_stage_completed`, and `unit_failed`.

Profiling uses the same structured stream as operational logging. Timing and
resource records are identified by their event and stage fields rather than by
a separate logging system. A stage-completion record may include
`duration_ms`, `items_processed`, `records_emitted`, and `failure`.
